# Phase 0 实测结果

本文件记录 Phase 0 四个里程碑的真实数字。每节都带可复现的命令与参数。

环境：Python 3.10.0、cv2 5.0.0、numpy 2.0.0、venv 位于 `.venv`（`--system-site-packages`）。

## 里程碑 0a：几何校验判别力（200 张合成库，暴力检索）

**结论：通过。误识别 0 例，正确命中率 100%。**

暴力检索不含词汇表、不含粗排，每个查询对全库逐个做 `verify_pair`，所以这个数字是**几何校验本身的判别力上限**，不掺任何检索变量。

复现命令：

```bash
.venv/bin/python .superpowers/sdd/2026-07-28-phase0-recognizer/measure-0a.py
```

参数：库规模 200、评估参考图 20 张、每张 10 个合成查询、seed=1，共 200 次查询 × 200 次 `verify_pair` = 4 万次几何校验。

```
样本总数    200
正确命中       200  100.00%  （目标 >= 95%）
误识别           0   0.000%  （目标 <= 0.1%）
漏检             0    0.00%
P95 延迟    4379.1 ms
结论        达标

[0a] 提取 ORB 特征耗时 1.4s，平均 300.0 个/张
[0a] 描述子库 2.3 MB（200 × 12008 字节）
[0a] 评估耗时 867.9s（4340 ms/查询，每次查询含 200 次 verify_pair）
```

### 判读

- **误识别 0 例是这一节最重要的结果。** §8.3 的三条判定（内点 ≥25、签名行列式在 [0.05, 20]、第一名 ≥ 第二名 1.5 倍）在 200 张库上没有产生任何假阳性。
- 正确命中率 100% 说明合成扰动的强度是合理的 —— 既没有弱到测不出东西，也没有强到连源图都匹配不上。
- **合成纹理图比真实家庭照片更容易区分，所以 100% 是乐观上界，不是预测。** 真实数字要等里程碑 0d。

### ⚠️ 由这次测量暴露出的延迟问题，以及随后的 `maxIters` 修正

4340 ms/查询 ÷ 200 次 `verify_pair` = 每次约 **21.7 ms**。推算两阶段 Top-20 精排 ≈ 434 ms，而 spec §8.4 的服务端目标是 **80 ms**。profile 结果推翻了我原本的猜测：

| 组件 | 耗时 |
|---|---|
| `BFMatcher(NORM_HAMMING, crossCheck=True)` 300×300 | 0.17 ms |
| `findHomography(..., cv2.RANSAC, 3.0)` | **20.74 ms** ← 99% |

**决定性的洞察：那 20 ms 只花在假匹配上，真匹配恒定约 0.34 ms。** RANSAC 自适应终止 —— 找到好模型就停，只在**不存在**好模型（照片对不匹配）时才烧满默认 2000 次迭代。Top-20 里 19 个是假匹配，390 ms 全在那 19 次上。

采纳 `RANSAC_MAX_ITERS = 200`（估计器不变，见计划文档「RANSAC 迭代上限降到 200」一节，其中也记录了为何**没有**选 `USAC_ACCURATE`）。

### 用 `maxIters=200` 重跑 0a 的结果

```bash
.venv/bin/python .superpowers/sdd/2026-07-28-phase0-recognizer/measure-0a.py
# 日志：.superpowers/sdd/2026-07-28-phase0-recognizer/measure-0a-maxiters200.log
```

| 指标 | `maxIters=2000` | `maxIters=200` |
|---|---|---|
| 正确命中 | 200（100.00%） | **199（99.50%）** |
| 误识别 | 0（0.000%） | **0（0.000%）** |
| 漏检 | 0（0.00%） | **1（0.50%）** |
| 每查询耗时 | 4340 ms | **565 ms**（7.7× 提速） |
| 全脚本 | 867.9 s | 112.9 s |

**重跑是必要的，我先前判断错了。** 我曾在计划的提交信息里写「拒绝机制不变，故 0a 不必重跑」。机制确实没变、13 个测试确实全部照旧通过 —— 但**指标变了**：丢了一个真匹配。

这恰好是预测过的那个代价被量化：`maxIters` 限制难例上的努力，内点率约 0.3 的边缘真匹配需要约 500 次迭代才有 99% 置信度，200 次覆盖不到，于是变成漏检。**每 200 个样本丢 1 个。**

判读：可接受。漏检 0.50% 远在 ≤4.9% 的预算内，误识别仍为 0 —— 代价落在正确的那一侧（漏检只让用户多举一秒手机）。**但里程碑 0d 若显示真实照片上漏检偏多，第一个该抬的就是这个数**，而抬它只在假匹配上花时间。

### 仍未达标的项

P95 延迟 534 ms 依然远超 80 ms —— 但这是**暴力检索**每查询 200 次 `verify_pair` 的必然结果，不是两阶段的数字。两阶段 Top-20 推算 20 × 2.4 ms ≈ **48 ms**，里程碑 0b 会给出真实值。

## 里程碑 0c：单目标 `.imgdb` 实测体积

**结论：约 4.2-4.4 KB/张。原估 30 KB，改架构阈值 200 KB —— 下发 `.imgdb` 的设计成立，且带宽估算可以往下修一个量级。**

`arcoreimg` 来源与校验：

```
https://raw.githubusercontent.com/google-ar/arcore-android-sdk/master/tools/arcoreimg/linux/arcoreimg
5273584 字节
sha256 2585423461c77c02d034ed5333c5054384a5d19ad212f581ad0274198ace60c0
ELF 64-bit LSB executable, x86-64
放置于 tools/arcoreimg（已 gitignore，不入库）
```

| 源图分辨率 | `eval-img` 分数 | 单目标 `.imgdb` |
|---|---|---|
| 1200×800 | 100 | 4290 字节 |
| 2400×1600 | 20 | 4377 字节 |
| 4000×3000 | 0 | 4237 字节 |

3 个目标建在同一个库里 = 12301 字节，即约 **4.1 KB/目标，线性增长**。

### 判读

- 体积与源图分辨率基本无关（4.2-4.4 KB），因为 `.imgdb` 存的是特征而不是像素。
- 4.2 KB 远低于 200 KB 阈值，所以「云端识别命中后只下发那一张的单目标库」这个方案完全成立。spec §4 里按 30 KB 估的带宽可以往下改。

### ⚠️ 反直觉行为：分辨率越高，`eval-img` 分数越低

同一图像内容，1200×800 得 100 分、2400×1600 得 20 分、4000×3000 得 0 分。

这是**合成生成器的产物**：`make()` 在 1/8 尺寸上生成噪声再上采样，放大后画面只剩低频，而 `arcoreimg` 的评分对特征的尺度密度敏感。真实照片在各个尺度都有高频细节，行为会完全不同。

**结论：合成图不能用来验证质量分闸门（`MIN_QUALITY_SCORE = 75`）。** Task 9 的单元测试一律走 fake 脚本；闸门的真实行为留到里程碑 0d 用真实照片验证。

### 另修正了计划里的一处接口错误

`arcoreimg build-db` **没有** `--input_image_path` 参数（计划早先版本猜错了）。真实接口：

```
build-db --input_image_list_path=<file> | --input_images_directory=<dir>
         --output_db_path=<file>
```

清单文件每行 `名称|绝对路径|物理宽度(米)`。**这意味着打印物理宽度是在建库时烘进 `.imgdb` 的**，客户端运行时不需要再用 `addImage(name, bitmap, widthInMeters)` 传一遍。`build_single_target_db` 因此增加了 `print_width_m` 参数（commit `81c89da`）。
